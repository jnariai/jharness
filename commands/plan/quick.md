# plan:quick

You plan a small feature in one pass and write **one file**:
`.spec/features/[slug]/PHASES.md`, executable by `scripts/ralph.sh`. No SPEC, no
clarifier, no contracts, no subagents. For a big or risky feature (many rules,
several contexts, a public API, multi-repo) use `/jharness:plan` instead.

## Input — `$ARGUMENTS`

```
$ARGUMENTS
```

| Input | Meaning |
|---|---|
| free text | the feature description |
| path to an existing file | Read it; its content is the description |
| empty | ask what to plan — do not proceed |

## Flow

### 1 — Read context

Read what exists, nothing more:

- `AGENTS.md`, `docs/agents/coding_guidelines.md`, `docs/agents/architecture.md`
- `.spec/init/project-description.md` when present (bounded contexts, stack)
- the code the feature touches — Glob/Grep for the models, routes, Actions or
  components named in the description, so every task names real paths

No `AGENTS.md` and no `docs/agents/` → warn once (`no architecture context — run
/jharness:ai-context for better plans`) and plan from the code.

### 2 — Draft and confirm

Derive:

- `summary` — one line
- `slug` — kebab-case, ≤ 50 chars
- `acceptance criteria` — 3–7 binary, testable statements; taken from the
  description when it has them, otherwise drafted and marked `(drafted)`
- `open questions` — only what blocks a correct plan, at most 3

Present all of it in one message; ask the open questions in the same
AskUserQuestion call. The developer confirms or corrects. Confirmed ACs are the
source of truth. Do not write before confirmation.

Scope turns out bigger than ~3 phases or ~10 tasks → say so and recommend
`/jharness:plan`, or splitting into smaller slices.

`.spec/features/[slug]/PHASES.md` already exists → ask: overwrite or stop.

### 3 — Write `PHASES.md`

`mkdir -p .spec/features/[slug]`, then Write:

```markdown
# Phases: [slug]

Generated by /plan:quick — run with `./ralph.sh .spec/features/[slug]/PHASES.md`.

**Goal:** <summary>

**Acceptance criteria:**
- AC1 — <binary statement>
- AC2 — ...

## Phase 1: <phase title>

Before implementing, read:
1. The header of `.spec/features/[slug]/PHASES.md` — goal and acceptance criteria
2. `AGENTS.md` and `docs/agents/coding_guidelines.md` — conventions every task follows

- [ ] T01 — <task title>
      Arquivos: `path/to/file.ext`
      Mudança: <what to do, one line>
      Cobre: AC1
      Acceptance criteria: <condition verifiable against the code>
      Testes: `path/to/test.ext` — <test case>
- [ ] T02 — ...

## Phase 2: <phase title>
...
```

Task rules:

- **Use-case slices** — one user intent per task, end to end (model method,
  Action, entry point, view), not one layer per task. On a project with the
  harness Laravel guidelines, use their layout and vocabulary.
- **Every task has tests**, backend feature tests first, one per rule: happy
  path, each business rule, authorization denied, invalid input. Name the test
  file and case.
- **Every AC is covered** by at least one task's `Cobre:`.
- **Each phase leaves the suite green** on its own. Sequential dependencies go
  in later phases; most quick plans are 1–3 phases.
- **Real paths only** — from the code you read, or new files following the
  existing layout. Never invent an API you have not seen in the code or docs.
- **Terse** — one line per field; ralph re-reads the file every phase.

Format contract (ralph rejects or truncates otherwise):

- Level-2 headings are only `## Phase N: <title>`, numbered from 1, no gaps.
- Every task is a `- [ ] ` checkbox with indented sub-lines (no leading `-`).
- Every task carries `Acceptance criteria:` — ralph's verifier checks it.
- Keep the field labels `Arquivos:` / `Mudança:` / `Cobre:` / `Testes:` —
  ralph's progress tracker reads `Arquivos:`.

### 4 — Verify on disk

```bash
F=.spec/features/[slug]/PHASES.md
test -f "$F"
grep -Eq '^## Phase [0-9]+: ' "$F"
[ -z "$(grep -E '^## ' "$F" | grep -Ev '^## Phase [0-9]+: ')" ]
[ "$(grep -c '^- \[ \]' "$F")" -eq "$(grep -c 'Acceptance criteria:' "$F")" ]
```

Any check fails → fix the file and re-run the checks.

### 5 — Summary

One line each: file path, phase count, task count, ACs covered. Close with the
handoff — this command never implements:

```
/jharness:ralph .spec/features/[slug]/PHASES.md
```

## Rules

- **Never write application code** — only `.spec/features/[slug]/PHASES.md`.
- **One checkpoint** — confirmation in step 2; no other questions unless the
  developer's answers open a real blocker.
- **No issue tracker**, no external fetch.
- **No git writes** — the developer reviews and commits.
- **No secrets** — `.env` is never read.
